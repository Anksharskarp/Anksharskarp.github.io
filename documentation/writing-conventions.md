# Writing conventions

These conventions reflect the site owner's explicit preference. They apply to
navigation, headings, buttons, descriptions, model labels, error messages, and blog
entries. The writing should be clear, direct, and natural. Do not use marketing-style
labels or slogans.

## Labels

Name the destination or action. Prefer short, familiar words. The theme belongs in
the visual design; visitors should not have to decode a fictional computer interface.
Terminal paths are fine as secondary visual labels when the main label is clear.

| Use                                                     | Avoid                                             |
| ------------------------------------------------------- | ------------------------------------------------- |
| Read article                                            | Read the engineering story                        |
| View source                                             | Explore the source                                |
| About                                                   | A little background                               |
| Contact                                                 | Have something in mind?                           |
| Projects                                                | From research to release                          |
| CPU socket                                              | The heart of computation                          |
| Managing video calls and session expiry in React Native | Keeping a call alive when the app has other plans |

## Descriptions and articles

- State what was built, your role, and the relevant result.
- Use concrete nouns and verbs. Explain technical terms when the reader needs them.
- Prefer ordinary connected sentences over slogans, rhetorical questions, or sentence fragments.
- Avoid promotional phrases such as “seamless,” “cutting-edge,” “unlock,” “reimagine,”
  “Python ergonomics, C/C++ performance,” and “built with intention.”
- Avoid anthropomorphism such as “the app has other plans.”
- Keep claims within the supplied evidence. Do not invent metrics, personal
  experiences, compliance certifications, model specifications, or outcomes.
- Distinguish a documented implementation from a suggestion or an untested case.
- Use ordinary paragraph text for explanations. Reserve monospace paths and command
  syntax for things that actually identify files, routes, code, or commands.

Example: “A Python financial mathematics package with a C/C++ backend. I implemented
time-series utilities and options-pricing models using pybind11.”

For the logic board, describe it as an illustrative model. MB-01 identifies the
illustration; it is not a manufactured board or a hardware project claimed on the résumé.
